# 规范智能问答助手系统 · 技术栈建议

## 设计目标

本方案围绕功能设计文档中的四类核心能力展开：流式问答、知识库管理、文档解析向量化、多 LLM 配置。在满足检索耗时 500ms 以内、50 并发、单文件 50MB 等非功能指标的前提下，把部署单元从六七个容器压到两个，用 `docker compose up -d` 一键起，未来加新页面只动代码不动架构。

## 精简思路

原方案包含 Nginx、API、Celery Worker、PostgreSQL、Redis、MinIO 六个容器。对一个单租户、工程规范文档量级的内部问答系统而言，其中三个可以裁掉：

| 裁掉的组件 | 替代方式 | 取舍依据 |
|------------|----------|----------|
| Nginx | **FastAPI** `StaticFiles` 直接托管前端构建产物，SSE 由 Uvicorn 透传 | 单服务小规模部署不需要独立反代；静态资源 gzip 可在 Uvicorn 层开启 |
| Celery + Redis | **FastAPI** `BackgroundTasks` + 进程内线程池处理文档解析 | 文档解析是低频写操作，单文档几秒到几十秒，后台任务足够；省掉一套消息中间件 |
| MinIO | 原始文档存宿主机 **volume 挂载目录** | 文档总量有限、无需 S3 协议，本地文件系统配持久化卷即可 |

裁剪后只剩两个容器：应用服务与数据库。Redis 的会话缓存职责由 PostgreSQL 直接承担——50 并发量级下，对话历史和会话状态走 PG 读写完全够用，热点知识库元数据可加进程内 LRU 缓存补足。

## 技术栈选型

| 层次 | 选型 | 作用 |
|------|------|------|
| 前端 | React + TypeScript + Vite + TailwindCSS + Ant Design | 对话主界面与后台管理页；Markdown 渲染用 `react-markdown`，SSE 用原生 `EventSource` |
| 后端 | Python 3.11 + FastAPI + Uvicorn | API 服务，同时通过 `StaticFiles` 托管前端，省去独立 Web 服务器 |
| 数据库 | PostgreSQL 16 + pgvector | 结构化业务数据与向量数据同库共存，少一个向量服务 |
| 文档解析 | MinerU（调用本地部署 API） | 已独立部署，通过 `POST /file_parse` 上传文件获取 Markdown；版面分析、表格识别、公式识别能力远优于通用解析库，尤其适合工程规范文档 |
| RAG 编排 | 直接调用各厂商 SDK，检索逻辑自实现 | 分块、Embedding、Top-K 检索、Prompt 拼接；多 LLM 提供商通过统一接口抽象 |
| 部署 | Docker + Docker Compose | 两容器编排，环境变量注入配置 |

## 架构总览

精简后的数据流只有一条主线和一个旁路：

```
浏览器 ──HTTPS──▶ FastAPI 应用服务 ──流式问答(RAG)──▶ LLM/嵌入服务
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
   PostgreSQL       本地文件卷      BackgroundTasks
   (业务+向量)      (原始文档)      (调用MinerU·分块·向量化)
                                       │
                                       ▼
                                  MinerU API
                                  (本地部署)
```

用户提问时，应用在 PostgreSQL 的 pgvector 中做相似度检索，召回 Top-K 文本片段，拼接系统提示词与用户问题后以 SSE 流式调用 LLM，前端实时渲染。文档上传走另一条路径：接口接收文件落盘后立即返回，`BackgroundTasks` 将文件提交至 MinerU 的 `POST /file_parse` 接口，获取包含版面结构的高质量 Markdown 文本，再按 500 字符或语义段落分块、Embedding 写回 pgvector，列表页轮询解析状态。MinerU 的版面分析与表格识别能力保证了工程规范文档中复杂排版的解析精度，这是后续检索质量的基础。

## Docker 部署

两个服务的编排骨架：

```yaml
services:
  app:
    build: .
    ports:
      - "80:8000"
    volumes:
      - ./uploads:/app/uploads        # 原始文档持久化
      - ./pgdata_shared:/app/dbdata   # 可选：数据导出
    environment:
      - DATABASE_URL=postgresql://app:app@db:5432/qa
      - LLM_ENCRYPT_KEY=${LLM_ENCRYPT_KEY}
      - MINERU_API_URL=http://<mineru-host>:8000
    depends_on:
      - db
  db:
    image: pgvector/pgvector:pg16
    environment:
      - POSTGRES_USER=app
      - POSTGRES_PASSWORD=app
      - POSTGRES_DB=qa
    volumes:
      - ./pgdata:/var/lib/postgresql/data
```

`app` 镜像内含前端构建产物与后端代码：构建阶段用 Node 编译前端 `dist`，运行阶段由 Uvicorn 同时提供 API 与静态文件。所有敏感配置（LLM 密钥、数据库连接串）通过 `.env` 注入，API 密钥落库前用 `cryptography` 对称加密，前端展示时脱敏。

## 扩展性预留

后端按 `routers/` 目录拆分模块——`chat`、`knowledge`、`admin` 各占一个文件，新增功能页面只需加一个 router 和对应数据表，不影响主链路。前端用 React Router 预留 `/chat`、`/admin`、`/services/*` 层级，新页面加路由即可。

当未来负载超出单机容量时，精简架构留有平滑升级路径：把 `BackgroundTasks` 换成 Celery + Redis 以承接大批量文档入库；把 pgvector 换成 Milvus/Qdrant 应对百万级向量；在应用前加 Nginx 做负载均衡。这些替换都是局部改动，因为检索层、异步层、解析层、静态托管层都已抽象为内部接口，切换实现不影响上层业务代码。MinerU 调用同样封装在统一解析接口之后，若后续需要支持更多文件格式或更换解析引擎，只需调整该接口的实现。
